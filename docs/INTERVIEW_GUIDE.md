# 第 1 课：整条链路的脉络

## 一句话总纲

> 我做了一个识别「论文工厂」的项目 —— 学术界的流水线式批量造假。
> 用 7.2 万条撤稿案底和 13.5 万篇被撤稿作品的引用轨迹，
> 回答三个问题：撤稿规模有多大？能不能提前识别流水线？造假的代价有多大？

## 类比：这是个厨房

| 阶段 | 厨房里对应的事 | 技术名词 |
|---|---|---|
| 采集 | 去菜市场买菜 | `ingest` |
| 数仓 | 洗菜、切菜、配菜 | `warehouse` |
| 分析 | 下锅炒 | `analysis` |
| 可视化 | 摆盘上桌 | `viz` |

"买菜"这一步藏着三个真问题，**这三句话就是采集层的全部内容**：

- **不能买太猛** —— 把菜市场搬空，下次人家不卖你了 → **令牌桶限流**
- **路上菜摔了要能重买** —— 但不能傻站在那儿一直重买 → **指数退避重试**
- **今天买过的别明天又买一遍** → **磁盘缓存**

## 核心问题：为什么要分三层？

面试官很可能问「**全写一个脚本里不行吗？**」

- 答"因为大家都这么分" → **0 分**
- 答出下面这段 → **加分**

> 分层的本质是**让变化被隔离在最小范围内**。
>
> 数据管道里会变的东西有三类，变化频率完全不同：
>
> 1. **上游数据格式**变了（对方加了一列）→ 只改 `staging`
> 2. **业务口径**变了（"撤稿时滞"从按天改成按月）→ 只改 `intermediate`
> 3. **想加一张新报表** → 只加一个 `marts` 文件，前面全不动
>
> 全写在一个 2000 行的脚本里的话，改一个口径就要重跑整条链路，
> 而且你**不敢改** —— 因为你不知道会碰坏什么。

## 一条真实记录的完整旅程（这是你的"杀手级演示"）

**Record ID 62150** —— 出自 `Journal of Healthcare Engineering`，2023 年被撤稿。

### ① RAW 层：原始 CSV

```
RetractionDate     = 10/4/2023 0:00          ← 字符串，美式格式，带假时间
Reason             = 11 个原因挤在一个字符串里，分号分隔 + 尾分号
Country            = Ethiopia;India          ← 多值挤在一起
RetractionPubMedID = 37829370                ← 数字被存成了字符串
Paywalled          = No                      ← 布尔值被存成了字符串
```

> 💡 这条记录的 `URLS` 字段里写着：
> *"Hindawi and Wiley to retract over 500 papers linked to peer review rings"*
> —— 面试时能讲出这个背景，说服力完全不同。

### ② STAGING 层：清洗

| | 变化 |
|---|---|
| `10/4/2023 0:00` → `2023-10-04` | 字符串变成真正的 **DATE** 类型 |
| `unavailable` / `0` → `NULL` | 哨兵值变成真缺失 |
| 多值字段保持原样 | 拆开是下一步的事 |

### ③ 多值展开：**一对多**（最容易错的地方）

11 个原因从一个字符串，摊成 **11 行**。

**为什么不拆开会出错？**

不拆的话，这条记录的 `reason` 就是一条 410 字符的超长字符串。
你 `GROUP BY reason` 时，它会被算成**一个独立的类别** ——
而其他 7 万条记录几乎不会有完全相同的组合。

结果就是排名里全是这种没用的东西：
> "Computer-Aided Content;Concerns about Data;Investigation by Third Party… 出现 1 次"

**拆开之后才能回答"哪种撤稿原因最常见"。**

代价：`72,453 条记录 → 281,827 行`（平均每条 3.9 个原因）。

### ④ INTERMEDIATE 层：算出派生字段

原始数据里**没有**"撤稿时滞"这个字段，它是我算出来的：

```
retraction_date       = 2023-10-04
original_paper_date   = 2022-03-26
retraction_latency_days = 557        ← 两个日期相减
```

同时把散落在 5 张展开表里的信息合并回来：
`n_reasons=11, n_authors=4, n_countries=2, n_institutions=4, is_paper_mill=True…`

### ⑤ MARTS 层：个体汇入整体

到了这一层，**"62150"这个个体消失了**。它变成了一行期刊统计：

```
journal                = Journal of Healthcare Engineering
publisher              = Hindawi
n_retractions          = 1,074
n_paper_mill           = 647          ← 其中 647 篇被标注为论文工厂
paper_mill_share       = 60.2%        ← 超过六成！
peak_year              = 2023
peak_year_retractions  = 1,013        ← 单年撤稿 1,013 篇
risk_score             = 93.96  → 极高风险
```

## 每一层的数据形态（理解全链路的关键）

| 层 | 数据长什么样 | 回答什么问题 | 这条记录的行数 |
|---|---|---|---|
| **raw** | 原封不动的 CSV / JSON | 「上游给了什么」 | 1 行 |
| **staging 主表** | 一行 = 一条原子事实 | 「数据长什么样」 | 1 行 |
| **staging 展开表** | 一行 = 记录 × 维度值 | 「维度怎么分布」 | **11 行** |
| **intermediate** | 已按业务口径加工 | 「指标怎么算」 | 1 行 |
| **marts** | 一张表回答一个业务问题 | 「所以呢？」 | 1 行（期刊级） |

## 面试标准答案：数据量怎么说

不要含糊说"很大"，给具体数字：

> 撤稿案底 72,453 条、被撤稿作品 135,584 篇、合作网络 106 万条边，
> 加起来约 130 万个核心数据点。
> 原始文件 138 MB，建完的 DuckDB 是 263 MB，32 张表。

## 2 分钟自我介绍模板

> 我做了一个叫 PaperMill Hunter 的项目，做的是识别「论文工厂」——
> 学术界那种流水线式的批量造假。
>
> 数据这边采了两块：Retraction Watch 的撤稿案底 7 万 2 千条，
> 和 OpenAlex 里 13 万 5 千篇被撤稿作品的完整引用轨迹。
>
> 拿到数据之后搭了一个三层数仓 ——
> staging 做清洗，intermediate 定业务口径，marts 出结果表。
> 分层是为了让变化被隔离，改一个口径不用重跑整条链路。
>
> 分析上做了三块：判断期刊是否可疑的异常检测、
> 用图算法找"挂名团伙"、用事件研究法量化撤稿的引用代价。
>
> 结论里最有意思的是：撤稿当年引用掉 23%，两年后掉到 72%；
> 论文工厂的论文跌得更狠，两年后掉 87%。

---

## 本课要记住的三个词

1. **分层隔离变化** —— 三类东西会变，变化频率不同，所以要分开
2. **一对多展开** —— 多值字段不拆开，统计结果毫无意义
3. **派生字段** —— 很多有信息量的指标（如撤稿时滞）原始数据里没有，是算出来的
